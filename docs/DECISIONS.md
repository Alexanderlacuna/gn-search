# Decisions

One row per choice that could have gone another way: the decision, the
alternative rejected, why, and the report line it follows. Report lines are
`file §section` in this directory (`docs/`).

Rows marked **open** are decisions this crate cannot make on its own — they
need an owner answer before the crate becomes a parity drop-in.

Rows are append-only: the row number is a permanent handle (comments and
reports cite it), so a new row joins its section's block with the next free
number rather than renumbering the ones below it.

## Grammar

| # | Decision | Alternative rejected | Why | Report line |
|---|---|---|---|---|
| 5 | The grammar is data (`GRAMMAR`) plus a pure renderer; no xapian dependency in the file. | Build the parser objects here, against `xapian_rs`. | The binding is a git-pinned fork, not a crate; a data table with a renderer is testable on a machine with no xapian, which is the only machine available. | SCOUT-NATIVE §3, §8 |
| 6 | The renderer emits flat `(prefix, term, kind)` triples; `ParsedQuery::raw` keeps the query verbatim. | Build an expression tree (grouping, precedence, phrases). | A tree is the backend's parser's job, and an un-compilable second parser is a liability. Total on every input: unknown tokens are free text. | SCOUT-NATIVE §3 |
| 7 | Boolean operators (`AND`/`OR`/`NOT`/`XOR`/`NEAR`/`ADJ`, uppercase only) render as their own `TermKind::Operator` leaf. | Treat them as free text, or drop them. | Dropping query text silently changes semantics; a leaf at least carries the token through, and lowercase forms stay plain terms. | SCOUT-NATIVE §3 |
| 8 | Boolean values are lowercased for ALL eight prefixes. | Lowercase only `group`, exactly as gn3 does. | The index stores only lowercase boolean terms, so mixed case matches nothing; gn3's narrower rule is parity-neutral because every graded shape is already lowercase. | SCOUT-NATIVE §3 |
| 9 | A numeric field value is a range ONLY when it contains `..` and is not quoted; a bare value is free text (`year:2014` is the words `year` and `2014`, `mean:5` is a `mean 5` phrase — row 34). | Render `<v>` as the point range `<v>..<v>` (this row's original text), or reject it. | Ground truth settles it: xapian consults a range processor only for range syntax, and GN4 asserts `!mean5.contains("VALUE")` — "`mean:5` is a `mean 5` phrase, never a range" (`native.rs:722-725`; the guard at `native.rs:389-405` inspects only values containing `..`). The old reading turned `year:2014` from a text query into a slot-5 range. | SCOUT-NATIVE §3; `native.rs:389-405`, `:722-725` |
| 10 | A numeric-range side that is not a number is a `RenderError`, surfacing as `InvalidQuery{message: "Unknown range operation", xapian_error_type: "QueryParserError"}`. | Return a generic internal error, or an empty result. | It is the recorded Q52 diagnostic and the 422 class GN4 already grades; anything else is a parity regression. | SCOUT-NATIVE §6 |
| 11 | An unparseable `position` value renders as a range with no bounds (matches nothing), not an error. | Raise `InvalidQuery`. | gn3's escaped `ValueError` is not a contract; the blessed behaviour for the class is a 200 with no hits. | SCOUT-NATIVE §3 (position processor), §6 |
| 12 | The document type rides on `ParsedQuery` (`with_type`/`type_term` → `XT{type}`). | Add a `type_` parameter to `Index::search`. | The assigned seam is `search(&q, limit, page)`; the filter has to travel with the query rather than widen the trait. | SYNTHESIS §3 (the four-tuple); SCOUT-INDEXER §2 (`XT` terms) |
| 13 | `Hs:`/`Mm:` are IN the grammar as species-location shorthands: `XShuman`/`XSmouse` ∧ `XC<chromosome>` ∧ a slot-2 range, no liftover, and an invalid value is `InvalidQuery`/`InvalidOperationError` (the Q42 422 class). | Leave them out (this row's original text), or port gn3's hg19→mm10 liftOver OR-branch. | The original row cited OPEN-4, but OPEN-4 is about *liftover*, not about the shorthands: GN4 registers both without it (`native.rs:151-170`, `LocationProcessor` `native.rs:310-350`). Leaving them out made Q40/Q41 return ~0 hits under a 200 and left Q42's error class unreachable. Liftover itself stays out (SYNTHESIS §7 Q3 still open to the owner). | SCOUT-NATIVE §3 (query builder), §6 (errors); SYNTHESIS §7 Q3 |
| 30 | A token whose field value is EMPTY (`position:`, `author:`, `Hs:`) is free text, not a field term and not match-nothing — the label is the word (row 34). | Render an empty value as a range with no bounds / an empty term. | An empty value never reaches a processor in gn3/xapian; the recorded Q53 `position:` is a 200 with 576 hits, and match-nothing would contradict it. | SCOUT-NATIVE §3 (`native.rs:264-270`) |
| 31 | Three syntax faults are rejected before any backend: a dangling operator (either end, or two in a row) and an unbalanced quote. `NOT` is a prefix operator, so it is exempt in leading position, after itself, and after a binary operator (`alcohol AND NOT dependence` and `a AND (NOT b)` render). | Keep the renderer total on every input. | GN4 answers the dangling-operator class with 422 `invalid_query` — the recorded Q51 diagnostic `"Syntax: <expression> AND <expression>"` — which a total renderer can never produce. The `NOT` exemption is a judgement: a prefix exclusion is meaningful and no fixture pins whether xapian accepts it, so the renderer does not invent a 422. Treating `NOT` after a binary operator as dangling was a spurious 422 until `REVIEW-FIXES.md` §d blocker 1 — a 422 where production answers is the direction a parity claim cannot afford. | SCOUT-NATIVE §6; corpus Q51; `REVIEW-FIXES.md` §d blocker 1 |
| 34 | An unconsumed `field:value` token renders as its WORDS: `year:2014` is the free-text terms `year` and `2014`, `position:` is the term `position`, `mean:"1..2"` is `mean` and `1..2`; an unregistered name (`foo:bar`, Q50) stays one term as written. The words of one field token carry `phrase` (row 36). | Keep the token as written — one free-text term `"year:2014"` (this row's predecessor, row 9's "free text" read literally) — or drop the label and keep only the value (`"2014"`). | The recorded evidence settles it, not taste: Q53 `position:` returned **576 documents**, which can only be hits on the word `position` (dropping the label leaves an empty query, which would match everything or nothing, not 576), and GN4 measures `mean:5` as a `mean 5` phrase (`native.rs:722-724`) — both words are in the query xapian builds. A quoted value is never range syntax (`native.rs:380-401`), so `mean:"1..2"` is phrase content, not the Q52 422. An unregistered name is not a field (nothing to split), so Q50 `foo:bar` is unchanged. The value's term never contains the label; the label is its own term. | `REVIEW-FIXES.md` §d blockers 3 and 4; `native.rs:380-401`, `:722-724`; corpus Q50, Q53 |
| 35 | A phrase (`"a b"`) or a positional operator (`NEAR`, `ADJ`) is UNREPRESENTABLE to the index this crate talks to: the renderer emits the words, marked `phrase` where they are adjacent (row 36), and the corpus runner skips those shapes by name (`phrase-not-expressible`) instead of grading or passing them. | Approximate a phrase as an AND of its words and call that parity, or grade the shape against the fixture double, which can only AND. | This index stores stemmed terms with no positions, so phrase and `NEAR`/`ADJ` queries parse and then match **zero** documents (`genenetwork4/docs/search-engines.md:98-102`; Q04/Q11/Q12 each recorded 0 hits). An AND-of-words is a different query that would match; the real backend must hand phrases to xapian's own parser, so nothing at term level can be parity for them — the marker makes the adjacency expressible to that parser, and the runner still refuses to grade it. | `REVIEW-FIXES.md` §d blocker 2 (runner evidence); `REVIEW-BLOCKERS.md` §5 blocker 2; `genenetwork4/docs/search-engines.md:98-102`; corpus Q04, Q11, Q12 |
| 36 | A rendered free-text term says whether it is one word of a PHRASE (`RenderedTerm::phrase`): the label and value of a field token the grammar does not consume (`mean:5` is the phrase `mean 5`), and the words of a quoted region. Consecutive `phrase` terms are ONE phrase, which the backend hands to xapian's own parser instead of ANDing. | Leave the words unmarked — an implicit AND — and keep the structure only in `ParsedQuery::raw`. | GN4 measures `mean:5` as a `mean 5` phrase (`native.rs:721-724`), and a phrase answers **0** hits on this positionless index (Q04/Q11/Q12), while an AND of the words matches a larger set — the false-positive direction a search API is judged on. The marker is the only term-level shape that can be parity, and it is what the corpus runner keys its skip on (`phrase-not-expressible`), so the `year:2014` class is skipped BY NAME rather than being silently graded: an implicit AND would have been indistinguishable from a real AND of two free-text words. | `REVIEW-BLOCKERS.md` §5 blocker 2; `native.rs:721-724`, `:376-385`, `:398-401`; corpus Q04, Q11, Q12, Q53; row 34 |
| 37 | Quote state is a property of the QUERY, not of the token: a token that STARTS inside a quoted region is phrase content — no field dispatch, no operator, no range parse — and a field value ENDS at the first quote (`mean:1.."2"` is the one-sided range `1..` plus the phrase word `2`). | Test the token's own first character (`value.starts_with('"')`), as the renderer first did. | GN4 decides it per query: its range guard walks the whole string with an `in_quotes` state machine (`native.rs:376-385`) and its value stops at a quote (`:399`). The per-token test made `"alcohol mean:abc..def"` a 422 where GN4 answers 200, and `mean:1.."2"` a 422 where GN4 parses a range — a false rejection, the one direction a parity claim cannot afford. | `REVIEW-BLOCKERS.md` §5 blocker 1; `native.rs:376-385`, `:399` |

## Index

| # | Decision | Alternative rejected | Why | Report line |
|---|---|---|---|---|
| 14 | `trait Index` is not object-safe (`Sized`, associated `open` returning `Self`). | `dyn Index` plus a factory. | A backend is chosen at build/config time; a vtable buys nothing and hides the concrete type whose pre-checks matter. | SCOUT-NATIVE §2 |
| 15 | The default backend is the in-memory fixture; `--features xapian` selects the stub instead. | Ship no default backend, or make xapian the default. | Every test must run with nothing external, and the xapian binding cannot be built here at all. | SCOUT-NATIVE §2, §8; BASELINE §1 |
| 16 | The fixture holds the five recorded alcohol hits, all `XTphenotype`; the type filter is proven by exclusion (a gene query returns nothing). | Synthesise a `gene` document. | No invented data: a synthetic gene hit would need a Geno/ProbeSet record nobody recorded. | SCOUT-NATIVE §7 (the 5-hit fixture) |
| 17 | The fixture matches boolean terms against the named hit fields, numeric terms against the slot's field, and approximates free text with a substring test; operators are ignored. | A term list and a real evaluator. | It is a test double for paging, type filtering and hit shape; a second scoring engine would be unverifiable without a compiler. | SCOUT-NATIVE §3, §4, §5 |
| 18 | The xapian stub performs the pre-checks and then panics with `unimplemented!` naming the missing binding. | Return `Err(Internal("not implemented"))`. | A silent error would let a caller treat a missing backend as a runtime condition; the assignment asks for a clear `unimplemented!`, and the pre-checks still carry GN4's exact messages. | SCOUT-NATIVE §2, §8 |
| 32 | The fixture (the default build's only backend) REFUSES a non-empty index path with `SearchError::Internal` naming `--features xapian`; only an empty path opens it. | Let `open` ignore the path, as it did first. | A build with no index reader that answered `/var/genenetwork/xapian` with the five recorded fixtures would fabricate search results — silent, plausible, wrong, and wrapped by the route in a good envelope. `Internal` is 500 on GN4's existing table, so no variant and no status is invented. | `REVIEW-CRATE.md` F1, §7; SCOUT-NATIVE §6 |
| 33 | `Index::search` returns the FULL match set from the page's offset; `limit` places the offset and truncation belongs to the caller (the route truncates to its `limit` or to `SORT_FETCH_LIMIT` = 1000). `limit == 0` and `limit == u64::MAX` both mean "from the top, unbounded". | Keep the page-sized contract (`offset`, `take`). | GN4's native engine retrieves `mset(first_item, u32::MAX)` and the route truncates; a page-sized engine makes the route's sorted path rank the first 1000 *relevance* hits instead of the whole match set, so `sort=lrs` would answer differently. | SCOUT-NATIVE §5; `native.rs:80,511,514`; `routes/search.rs:214-233` |
